# 认知决策日记：Profile 模式的资源调度瓶颈——用户控制与现实实现之间的认知落差

  记录日期：2026-06-02

  事件触发：Agent 平台化产品架构评审——Profile 模式在用户接入场景下暴露出资源调度瓶颈

  核心冲击点：为什么 Profile 模式最终会遇到资源调度瓶颈。

---

## 背景

  当前公司正在进行 agent 平台化产品开发，研发采用的是 hermes agent 作为调度运行的运行时架子。研发已经基于 hermes agent 接入业务 skill 测试 agent 锁定 skill 并执行了。产品介入，提出要做用户接入，但是 hermes agent 自身不支持网关加数据逻辑隔离，默认提供 profile 单用户进程隔离模式。

---

## 认知过程

  接下来就产品未来目标愿景倒推 profile 模式是否可行？我协助暴露这个用户控制和现实实现之间的差距，并对两种方案从多个维度给出了对比，最终给出决策问题清单，组织评审决策。

---

## 决策过程

  我先针对理想方案和当前方案分别从实现难度、数据模式、对产品几个核心实现目标的影响等方向上进行对比分析，然后再罗列影响方案决策的关键问题清单，比如当前时间窗口，远期目标支持度，如果支持需要改造的工作量；各自无法支持的产品场景是什么？最终再来决策本期方案是什么？远期方案是什么？如果要迭代支持，则排期方案是什么？是否要预留迭代设计。

  一开始我以为产品经理和研发评审都是这么干的，但实际是当研发说做不了，产品就会迁就研发的方案，甚至未曾考虑过为什么做不了，研发给的方案和产品目标之间有多大的差距。

---

## 两种方案对比

  在 hermes agent 自带的 profile 隔离方案这个实际问题上，对比方案是前端用户统一网关，但 agent 实例多 session 逻辑隔离。二者的优劣势都非常明显：

  **Profile 方案：**
  - 隔离更为彻底，用户之间进程级别硬隔离
  - 单个用户服务异常不影响其他用户
  - 非常适合的场景是个人智能助手
  - hermnes agent yuan 原生支持
  - 智能进化默认也是个人用户的进化，无法做到组织间进化，除非外加数据聚合进化能力来做
  - 用户的任务也是进程隔离，难以做到任务级别的资源分配

  **统一网关 + 单实例多 session 逻辑隔离方案：**
  - 把用户 session、任务、记忆、技能全部统一管理，通过用户权限进行控制
  - 优势在于数据集中管理多用户的相同任务轨迹可以共同进化
  - 资源调度管理的单元粒度可以更小
  - 不足就在于需要重新开发，增加用户和 session 表映射，性能会受到影响
  - 用户数据隔离不够彻底，需要对隐私要求高的场景增加较强的权限校验管理支持

---

## 深层需求

  随着逐渐思考得出更深层次的需求，当 agent 具备稳定自动化完成任务的能力之后，批量自动化任务发起成为必然，这个时候资源管理（算力、存储）成为刚需，profile 模式无法支持智能运维调度。

---

## 决策结果

  本期由于时间窗口是最大的问题，选定按找 profile 模式先接入具体业务进行自进化流程走通。

  产品经理后续基于产品目标设计数据管理方案。

---

## 暴露问题动机

  我暴露问题的本心并不在于证明谁对谁错，只在于评判选定不同方案，解决问题的阶段不同。另外如果某一个方案在远期不足以支持，债务会越来越多，倾向于产品尽快决策选定方案并进行排期安排。

---

## 方案决策思考

  作为产品经理，对于研发说做不了，我们不是去否定别人的能力，而要从现实出发一起分析做不了的原因，去挖背后真正的限制，往往通往正确的路就在这些背后限制里面。即使最终降级处理也要往实现产品最终目标的方向努力，而非直接接受方案，最终导致产品实现和实际目标差距越来越大。

---

## 认知盲点记录

  后续这个产品的用户体量规模我不确定，只知道是部署在内网。

  数据逻辑隔离，当用户量大、并发任务产出数据量（文本量）足够大时，找到用户的 session 等等速度降低，需要探索有什么好的解决方案。

  逻辑隔离是否能够满足极度要求隐私的任务或者数据处理，这时是否针对性的做 profile 支持。
